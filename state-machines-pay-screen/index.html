The pay screen

What the customer sees while paying for a film. Before and after.

By Guy Eden

Before

Four places, each with its own idea

The bad moment: the checkout says completed, then the server learns the payment failed.

Page memory"I'm paid"
Screen label"Unlocking soon"
Tab storage"Never show Buy"
Server record"It failed"

Nobody asked the server. The customer waits forever, with no film and no Buy button.

After

One state, and the moves between them

normal server grants payment fails added by the fix
1 stateinstead of four places
No contradictionsevery move is named
Late grant still worksthe token is always kept

What changes

Before
  • Seven label words, two memory flags and four stored fields describe one payment.
  • Each event sets the pieces it remembers to set.
  • "Paid on the page, failed on the server" can happen and nothing flags it.
  • The rule "a paid key is never given up" is spread over several checks.
After
  • Ten states, written once, with the moves between them.
  • One function takes the state and an event and returns the next state.
  • An event that is not legal in a state is ignored, and a test says so.
  • The held token is kept through every move, so a late grant is always honoured.

The dashed move is in the code with a test that fails on the old code, and the one-state owner around it is built: a page table, a server purchase table, and a commit check against other writers.
