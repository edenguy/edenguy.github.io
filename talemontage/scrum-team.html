The scrum team, and the day it stopped waiting

A record of 2026-10-21, the day the queue first ran, brought up to 2026-10-22, the day the waiting left the personas: the roles, the queue they pull from, what the work costs, and what is still broken or in flight.

By Guy Eden · first read at 12:08 on 2026-10-21, read again at 07:57 on 2026-10-22 · docs/team/index.html

5 roles + a Python supervisor 2 models 99 items 83 merged no session while nothing waits

What this is

A memory of a moment, kept because the shape of the team changes and a shape nobody wrote down teaches nothing. This page keeps both days: how it first ran, and what the second day changed.

For months TaleMontage was built by one session talking to its owner. The standing rule was already that the main session should plan, disperse and merge while background agents write the code — and the rule kept failing, not because anyone forgot it, but because every single step looked too small to be worth handing out, and a chain of small steps became the whole job.

On 2026-10-21 that rule stopped being a rule and became a machine: a queue on disk, four agent personas that pull work out of it rather than being handed it, a main session that only stocks the queue and merges what comes back, and two hooks that refuse the main session's own edits so it cannot quietly do the work itself.

On 2026-10-22 the machine was redesigned around two measurements from its first day. The worktree is now the item's state: claim makes it, a dead agent's uncommitted work is committed and the next claimant continues from it, and the merge removes it. Waiting is now Python, not a model: a supervisor polls the queue on disk and starts a headless persona only when an item needs its judgment, so an idle reviewer costs nothing. Every number on this page was read from the repository and the queue's own accounting at the time of writing; where a figure is an estimate, it says so, and where something is still broken or still in flight, it says that too.

The one invariant that makes it safe

A merge conflict becomes a refusal at claim time.

The owner's instruction for parallel agents was always “disperse by file, not by topic”: two agents in one module is a merge conflict he pays for twice. Every other part of this design exists to serve one mechanical consequence of that sentence.

A specced item carries the exact files it owns, and a claim whose files intersect a live claim's is refused. Not warned about — refused, by workpipe/store.py's claim, which tells the starved worker which file and which item held it back so it waits instead of inventing something to do.

A claim lasts until the merge. An item's files stay owned through claimed, submitted, reviewing, returned and verified, because a verified branch that has not been merged yet still conflicts with anyone editing those lines.

Item A — claimed by worker s3

  • scripts/story_build/build_story.py

What happens next

claim exits 6 — “items wait but another worker owns a file each of them needs” — naming the file and the item. Under the supervisor this is asked before any worker is started (ready --role worker is the same check with no model behind it), so a worker is only ever started for an item it can actually claim.

The side effect is a discipline on the planner: it refuses to spec an item it cannot give a non-intersecting file list. Work that cannot be separated by file has to be decomposed until it can, or given to one item. That is the whole of the merge-conflict problem, solved before any code is written.

The team

Four agent personas in ~/.claude/agents/work-*.md, a Python supervisor, and the main session. The model and the effort below are each file's own front matter, not a guess.

planner Sonnethigh effort

Turns a line of open work into a brief a worker can finish without asking anything.

File
~/.claude/agents/work-planner.md
Also
this queue's scrum master, and there is no second persona for it
  • Reads the code — most of its work. A brief whose file list is a guess costs more than it saves.
  • Each brief carries the goal, the exact files the item owns, the measurements already taken, the rules it must not break, a risk grade with its reason, the item's prerequisites, which tests to run and what to report.
  • Keeps the queue stocked and prioritised so workers pull rather than wait, and reports stalled work.
  • Writes no product code.

architect Sonnethigh effort

Decides, once, what shape a piece of work takes — before any worker starts.

File
~/.claude/agents/work-architect.md
When
only for an item carrying needs_contract
  • Not in the ordinary path, by design. The default is that nothing asks for a contract: a contract for a one-file fix buys nothing and costs a whole stage.
  • Writes a versioned, hashed contract — the decision, the shapes other work depends on, who owns which boundary, the invariants, the order items land in.
  • A worker cannot edit that contract to describe what it built: the hashes are compared.
  • Writes no product code and no test. Two items have used it, of 99.

worker Sonnetmedium effort

Claims one item no other claim blocks and does it, in the item's own worktree.

File
~/.claude/agents/work-worker.md
Where
the item's worktree, C:\dev\tm-<item id> on wq/<item id>, made by claim
  • Is not handed work: it pulls. Under the supervisor it is started only when an item is claimable, does that one item and ends.
  • Never makes a worktree. claim makes it, or reattaches the one a previous holder left — commits and all — and records both on the item.
  • Works from the brief alone, implements and tests its own item, commits there and submits. submit takes the commit from the item's tree and refuses a dirty tree, another tree or branch, and any file the item does not own.
  • Never merges, never touches the main branch, never edits a file outside its claim.

reviewer Fablemedium effort

Reads each submitted commit against its own brief, and decides.

File
~/.claude/agents/work-reviewer.md
Verdicts
verified · returned · blocked
  • A worker does not grade its own work: a verified item is one the reviewer verified.
  • Risk-based, not mandatory. It is never handed an item the planner graded low risk that touches nothing the project always reviews and has never been returned; those merge straight from submitted, and the item records why.
  • Asks three questions: does the diff do what the item asked, does it keep the project's rules and the guarantees the brief names, is anything in it nobody asked for.
  • Changes nothing. Never repairs a fix itself — returned carries the reasons and the item is claimed again.
  • Costs nothing while idle. On the first day 36% of its turns only asked whether there was work; it is now started per submitted item and ends with it.

the supervisor Pythonno model

The loop that waits, so no persona has to.

File
~/.claude/scripts/workpipe/supervise.py
Run as
wq supervise --workers 3 --merge, one background command
  • Polls the queue on disk, takes back claims whose holders are evidenced gone, and starts a persona only for an item that needs its judgment: a worker per claimable item up to --workers, one planner, architect and reviewer at a time.
  • Each persona is a headless session run as the persona: claude --agent work-reviewer -p "<take one item, judge it, end>", with the project's cwd, --output-format json, CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0 and --dangerously-skip-permissions: a headless session has nobody at the keyboard to answer a permission prompt, so one would hang the spawn; the nightly review (tools/cr_night.cmd) starts its session the same way for the same reason.
  • --merge runs merge --all's every gate as items become mergeable and reports a refusal rather than guessing at it. It decides nothing about any item.
  • Runs until nothing more can move without a person and exits with a summary: 0 settled, 7 a person is needed, 5 a bound was reached. Its exit is the main session's notification.

the main session the owner's session

The owner's counterpart, and the only part of the team he talks to.

Does
stocks the queue, starts the supervisor, launches builds in a visible console, answers the owner
Guarded by
.claude/hooks/delegate_guard.py
  • Puts work into the queue; it does not allocate it. Nobody hands work out — the personas pull.
  • Keeps what the hard rules reserve for it: launching a build, a pipeline stage or a journey in a console the owner watches; the checkpoint and the heavy suites; judging a refused merge; judging a film's artifacts.
  • Resolves what waits for a person: needs-owner, blocked, a claim the queue cannot check.
  • Does not write product code — and on this machine is refused if it tries.
  • Runs on whatever model the owner's session has (Opus 5 on the first day, Sonnet 5.5 on the second, read from the commits' trailers).

Why these models. The split follows the cost rule already written down for the bug pipeline: Fable for the roles that read and judge, Sonnet for the roles that write. So the reviewer is Fable and the planner, architect and workers are Sonnet. The bug pipeline's files say the same: bug-prover, verifier and code-reviewer on Fable; architect, triage, mitigator, test-writer and chaos-monkey on Sonnet. Nothing about the team's shape is more consequential than this line, and nothing in it is a preference: it is the measured cost of a day like the first one. The supervisor has no model at all, which is the second day's whole point.

How an item moves

The states are workpipe/stages.py's and store.py's, not a description of them. Each arrow is a command the script performs; the agents only judge.

  1. queuedA line of the project's open work. No spec yet.
  2. speccing → speccedThe planner reads the code and writes the brief with the exact files the item owns, its risk and its prerequisites.
  3. designing → contractedOnly if the item asked: the architect's versioned, hashed contract.
  4. claimedclaim makes the item's worktree and branch, records them on the item, and a worker owns it and its files. Never offered while a prerequisite is unmerged.
  5. submittedCommitted in the item's worktree, inside the files it claimed.
  6. reviewing → verifiedRead against the brief. Low risk skips straight to the merge.
  7. mergedTried on the main branch's head in a throwaway worktree first; then the item's tree is removed and its branch deleted, when the tree is clean and the branch has landed.

And the ways out

ExitWhat it meansWho picks it up
returnedSent back with reasons; it still holds its files and its worktreeThe next worker to claim it continues in that same tree
blockedThe work cannot proceed (a brief that contradicts itself, a dependency that is not there)The main session, not the worker
needs-ownerThe intended behaviour is a product decisionThe owner, asked by the main session; the answer comes back through resolve
droppedNot worth doing after reading the codeNobody. Two items have ended here
a reclaimThe holder is evidenced gone: no turn, no heartbeat, no claim for thirty minutesThe sweep commits its uncommitted work as WIP: on the item's branch; the queue adopts, and the next claim is bound to the same tree. recover --to redo is an explicit order to start afresh

No agent turns uncertainty into a product decision, and a stalled item is reported rather than worked around. Running long is never evidence that a holder is gone: an L item ran over an hour and was alive throughout. A claim whose holder the queue cannot recognise is never taken back automatically — it is named in status for a person to release.

The machinery

5,095 lines of Python at the user level, so it works in any repository (2,757 on the first day). It was modelled line for line on the bug pipeline (bug_queue.py, bugpipe/) so that the states, the commands and the exit codes feel the same to anyone who has used that.

The cleaners

What used to pile up now goes when its work has landed.

  • wq merge removes the item's tree and deletes its branch (git branch -d) when the tree is clean and the branch is an ancestor of the main branch; otherwise the reason is recorded on the item and the merge stands.
  • wq prune lists every tree and branch of the queue's shape with its item's state; --sweep removes only the merged, clean, landed ones. bug_queue.py prune does the same for a finished bug's fix branches, its mitigator's tree and its dead verify trees.
  • TaleMontage's tools/git_tidy.py, run by .githooks/post-merge after a merge on main, asks both queues to prune first and then sweeps what no queue accounts for. Nothing of an unfinished item or bug, a dirty tree, or a branch holding a commit main does not is ever touched. 31 worktrees and 44 branches had piled up before this.

Waiting is Python, not an LLM

The second day's change, and the measurement that forced it.

An idle agent costs nearly what a busy one does: every turn re-reads its whole conversation, so a turn spent asking “is there anything yet?” is charged at that agent's full context. The blocking waits added on the first day (wait, claim --wait, take --wait: a real sleep in the script) took the asking out of the personas, but still left a live session per persona, and every wake-up of one was a turn.

The dollars are a scale, not a bill: in + 5 out + 1.25 cache-write + 0.1 cache-read, priced per model from the cost records the harness keeps on this machine, with Fable's rate uncertain to about ±40%. A “waiting” turn is one whose only tool calls asked the queue for work.

So the loop is wait → claim → think → submit, and only think needs a model. wq supervise is the wait: a Python process with no context, whose wake-ups are free, and which starts a session only when store answers yes to a deterministic question — is an item queued, specced and asking for a contract, claimable, submitted and not review-optional. The session it starts is paid for only while it holds an item.

What a spawn costs, measured: one headless reviewer with one turn and no tool pays 13,544 cache-write tokens, $0.27 at Fable's list rate — the orientation a fresh persona pays once per item. The reused reviewer of the first run read 245M cached tokens over 592 turns, 414,000 a turn. That arithmetic is why one persona per item is the default and a persona kept alive for many items is not.

Tuning the shape of the team

The point of writing any of this down. workpipe/schemas.py holds a registry of persona sets, and every commit records which one handled its item — so a change to the team can be measured instead of argued about.

A schema reads queue/planner+worker+reviewer@2: the workflow, the persona set in the order the queue applies them, and the version of that set's definition in the registry. It is derived from the item's own history, which records every transition and the role that made it, and never from a configuration somebody typed — a session that thinks well of itself cannot label its work with a schema it did not use. Whether the item was independently reviewed is kept out of the schema and recorded separately, because an item that skipped its review is not the same data point as one that passed it. How the personas waited is a third field, runtime (poll on the first day, wait/1 since), because that costs or saves more than any difference between two team shapes.

It says nothing about whether the architect stage is worth its cost. That question needs the paired-replay pilot, which is why the pilot exists and why it refuses to report a comparison it has not measured.

The workflow is derived, never declared: a commit whose sha is on a queue item, or made on a branch an item owns, is queue work; one made in an agent's scope on a branch no item owns is delegated; one in the main session's own scope is direct. Of the 199 trailers, 54 say queue, 32 delegated and 108 direct — the last being mostly merges, backlog edits and the owner's own records.

The honesty is the design. The figure is called a session token delta and not a cost, because that is what it measures: the usage the committing session recorded between its previous measured commit and this one. It is not the causal cost of implementing the commit — the same session reads files, answers questions, runs tests and abandons attempts in that window. A name claiming causality would be used as though it had it.

It says provisional every time, because at the moment a commit message is written the current turn may not be in the transcript yet and the last message's output count is still growing; the settled figure goes to a ledger when the agent stops. A merge commit carries work done elsewhere and says not-measured rather than claiming the window as its own. And no trailer ever carries a path, a transcript, a prompt, a result or a secret — a session id and an agent id are opaque, and are the only identity recorded. It cannot fail a commit: it catches everything and exits 0 whatever happens.

Pricing each commit from its trailer is a queued item, not a tool yet: 20261022-074126-a-tool-prices-every-commit-from-its-sess is specced and tools/commit_cost.py does not exist on main as this is read.

The guards, and why they had to exist

The rule failed on the action, not on the judgement — so the action is what is refused.

delegate_guard.py this project

Refuses an Edit, Write, MultiEdit or NotebookEdit on TaleMontage's own source in the main worktree.

Where
.claude/hooks/delegate_guard.py
  • Allows every agent worktree (C:\dev\tm-* and the in-repo ones), or it would deny the very work the rule asks for. That prefix is why .claude/quality.json names worktree_prefix: "tm", so the queue's trees land where the guard allows them.
  • Allows the project's records — BACKLOG.md, CHANGELOG.md, docs/.
  • Fails open on purpose: an unknown tool-input shape, a missing field or a relative path ends in “allow”, because a hook that crashes blocks work it was never meant to judge.
  • There is a deliberate escape for a merge-conflict resolution or a genuine one-liner: creating .claude/allow-main-edit by hand, which is a conscious act, and is removed again after.

delegate_shell_guard.py any project

The same refusal for a write made through the shell, which the editing-tool guard never sees.

Where
~/.claude/scripts/delegate_shell_guard.py
  • sed -i customer/app.py, a redirection into a tracked file, a python -c that opens one for writing — holes demonstrated within an hour of the first guard being built.
  • A narrow list of obvious writers, not every shell command: judging whether an arbitrary command writes a tracked file is guesswork, and a false deny would block the agents the rule depends on.
  • It is a fence against the easy escape, not a proof, and says so.

What was broken on the first day, and what closed it

A memory that only flatters is worth nothing. The first day's page named three open faults; each was checked against the code again on the second day.

Closed — dependencies are now read. depends_on was recorded and consumed nowhere, so the queue handed out work whose files did not exist yet. Now depends.py: only a merged prerequisite satisfies a dependency, claim never offers an item whose prerequisites are unmet, spec refuses a cycle, and a chain that will not clear (a prerequisite dropped, blocked or sent to the owner) is reported in list, deps and doctor rather than silently waited on.

Closed — a claim no longer outlives its worker. leases.py: a claim names its holder and carries a generation; liveness is evidenced by a turn in the holder's transcript, a heartbeat or a claim, never inferred from elapsed time; a claim with none for thirty minutes is taken back, its uncommitted work committed as WIP: first, and a holder that wakes from a long freeze is refused by its stale token rather than by a guess.

Closed — one id inside another. store.new_id puts the discriminator between the stamp and the slug, and the accounting's alternation is bounded and tries the longest id first. A test holds both.

Closed — worktrees and branches piled up. Seventeen stale trees had to be matched to their items by commit subject after the first run. Now the tree is the item's, the merge removes it, prune sweeps earlier runs, and the project's post-merge tidy asks both queues first.

What is still open or in flight

Open — three live claims the queue cannot check. wq status as read names three holders it could not recognise (not-found), so their liveness cannot be evidenced and they are a person's to release. The safety mechanism held — nothing was taken back on a guess — but the detector did not recognise these holders, and why is not yet written down.

In flight — the owner's no-gates order. On 2026-10-22 the owner ordered that cinematic work ships on, with no tuning key to open it, and that the committed defaults take the sandbox overlay's values. The item that does it and rewrites docs/reference/TUNING_GATES.md accordingly (20261022-070638-lift-every-cinematic-gate-the-committed-) was returned by the reviewer once and waits for its second attempt as this is read; that file still carries its old register until the item merges.

In flight — the per-commit price (tools/commit_cost.py, queued, above) and the bug pipeline's supervisor (branch bug-supervisor, above).

Worth keeping in mind

What stays judgment, on purpose. The spec, the design, the change and the verdict are a model's: a planner reading code to write a brief, an architect choosing a shape, a worker implementing, a reviewer reading a diff against a brief. The supervisor, the leases, the dependencies, the worktrees and the merge gates are scripts, because each is a deterministic question the files on disk can answer. Nothing that can be answered without a model is asked of one; nothing that needs one is pretended to be a script.

Why the planner is also the scrum master, and why there is no fourth watching persona. Keeping the queue stocked, ordered and decomposed, giving each item verified file paths, and keeping two items out of one module are all the same work as reading the code to write a brief. The watching half is script work — and since the second day it is the supervisor's.

Why the reviewer is a persona and not a step of submit. In the bug pipeline the verifier earns its place because a proof is mechanical: red before the fix, green after. Dev work has no proof. The script can only show that a commit stayed inside its claim and that the worker says the tests passed — which a change that does nothing the brief asked also satisfies. Without the reviewer, verified would mean “it compiled”, and the main session would have to read every diff, which is the session doing the work again.

A shared registry file belongs to one item, not to every item. Three items that each add a row to one configuration file cannot each commit that row — a worker may only commit files its item owns — so the file would serialise all three behind one claim. Each item adds its own key in code with a safe default and reports the row it needs; one further item owns the registry file and writes every row at once.

Never cite a line number in a record file. BACKLOG.md and CHANGELOG.md move under an item as a matter of course, because every worker writes to them. A measurement saying “BACKLOG.md:214” is wrong by the time the item is claimed, and it has already sent workers to the wrong entry. Cite the entry by its title. A line number in code is a measurement and is welcome.
