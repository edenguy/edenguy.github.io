The scrum team

One owner, one session he talks to, a work queue on disk, and short-lived AI personas that pull items out of it and do them each in its own git worktree — with Python, not a model, doing all the waiting. Read at 08:24 on 2026-10-22; the details are a page of their own.

Five things to know

  • How an item flows. wq add puts a line of work in the queue. The planner writes its brief with the exact files it owns. A worker claims it, works in the item's own worktree, commits and submits. The reviewer verifies or returns it. wq merge brings it into main and removes the tree.
  • Why a worktree per item. Two agents in one file is a merge conflict paid for twice. A claim that touches a file another live claim owns is refused, and each item's commits live in its own tree until merged.
  • Why a fresh agent per item. Every turn of a long-lived agent re-reads its whole history: the first day's reused reviewer read 414,000 cached tokens a turn; a fresh one pays about 14,000 once. So a persona is started for one item and ends with it, and the main session is handed over at natural breaks.
  • Script or model. Waiting, claiming, checking a claim's files, the merge gates, the lease sweep and the cost trailer are Python. Only the brief, the change and the verdict come from a model (planner, architect and workers on Sonnet; the reviewer on Fable).
  • What the main session still does. Answers the owner, stocks the queue, starts the supervisor, launches builds in a visible console, resolves what needs a person, runs the checkpoint. It is refused if it edits product code itself.
